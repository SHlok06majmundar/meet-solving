# Nexus Meet

React and Express video meetings with WebRTC, chat, screen sharing, captions, recording, and optional meeting intelligence. Clerk manages accounts; the backend verifies sessions and controls database access.

## Development

Use Node.js **22.13 or later**. CI checks Node 22 and 24.

```sh
npm ci --prefix backend
npm ci --prefix frontend
```

Copy `backend/.env.example` to `backend/.env` and `frontend/.env.example` to `frontend/.env`. Set your Clerk publishable key in the frontend and the matching secret key or JWT public key in the backend. Set `CLERK_ISSUER_URL` to your Clerk token issuer. Never put backend secrets in a `VITE_` variable.

Run in separate terminals:

```sh
npm run dev:backend
npm run dev:frontend
```

Open http://localhost:5173. Without Supabase, development uses bounded temporary storage that loses data on restart. Local invitations expire after 24 hours. Production requires durable database storage.

## Authentication and invitations

The landing page is public. Dashboard and meeting routes require sign-in. New meetings use full random UUIDs generated by the backend. The frontend never invents an ID when the server is unavailable.

A meeting link is an invitation: anyone who possesses it and signs in can join. Treat invitation links as private. This is link-based admission, without host approval or an organization allowlist. Joining adds the verified user to the membership table; transcript and intelligence routes require membership.

API tokens and socket connections verify Clerk signatures, expiry, authorized origins, and session identity. Socket session tokens refresh during a call. Author IDs come from verified sessions, preventing clients from minting another user's video token or overwriting their transcript chunks.

Old eight-character invitation IDs are retired. Create new invitations in the dashboard. Existing transcript content is retained by the migration, but old meeting ownership is not automatically assigned or exposed to new accounts.

## Database migration

Back up the database, then run [supabase-schema.sql](supabase-schema.sql) in the Supabase SQL editor as the database owner. The transaction can be applied repeatedly. It creates or updates profiles, transcripts, meetings, memberships, intelligence, and AI chat history.

Row-level security is enabled and browser roles have no table privileges. The backend service-role client performs database operations after verifying identity and membership. Clerk remains the authoritative profile source; direct browser profile synchronization has been removed.

The transcript primary key becomes `(meeting_id, user_id, transcript_id)`. Keyset pagination handles equal timestamps without skipping chunks. Database failures return an error rather than claiming a temporary in-memory copy is durable.

Legacy installs with identity keys are supported. Repeated or missing transcript IDs receive new legacy IDs while every transcript row is retained. The retired `meeting_chat` table remains private with its history preserved. Existing insights tables gain a unique meeting index for explicit upserts. Legacy profile triggers have a fixed search path and cannot be called by browser roles.

## Production rollout

Coordinate the frontend, backend, and database cutover: the previous frontend's direct database writes stop working after browser privileges are revoked. Validate in staging, then use a short maintenance window.

1. Back up the database and apply `supabase-schema.sql`.
2. Configure backend variables below. Deploy **one backend instance** from `backend/`, using `npm ci --omit=dev` and `npm start`.
3. Configure `VITE_API_URL` and `VITE_CLERK_PUBLISHABLE_KEY`; deploy the frontend from `frontend/` using `npm ci` and `npm run build`. Serve `frontend/dist` with the supplied SPA rewrites.
4. Check `/api/status` and `/api/ready`. An unsigned request to `/api/generate-meeting-id` must return 401.
5. Sign in with two accounts, create a new invitation, and check audio, video, chat, captions, screen sharing, recording, and reconnection on separate devices and networks. Include a restricted network that requires TURN.
6. Restart the backend and confirm members can still retrieve transcripts and generated intelligence.

Required backend production settings:

| Variable | Purpose |
| --- | --- |
| `NODE_ENV=production` | Strict startup configuration |
| `ALLOWED_ORIGINS` | Exact HTTPS frontend origins, comma-separated; no wildcards or trailing slash |
| `CLERK_SECRET_KEY` or `CLERK_JWT_KEY` | Matching session verification secret or PEM public key |
| `CLERK_ISSUER_URL` | Exact expected token issuer |
| `SUPABASE_URL` | Database project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Backend-only database secret |
| `TURN_URLS` | Comma-separated `turn:` or `turns:` relay endpoints |
| `TURN_SHARED_SECRET` | At least 32 characters; must match coturn's `static-auth-secret` with `use-auth-secret` enabled |

Set `TRUST_PROXY_HOPS` to the exact trusted reverse-proxy hop count (for example, 1 behind one proxy). Leave 0 for direct access. Terminate HTTPS at the hosting proxy, or supply both `SSL_KEY_PATH` and `SSL_CERT_PATH`; unreadable explicit certificates fail closed.

TURN credentials last one hour. The shared secret stays on the backend. Development without TURN uses STUN only and can fail on restrictive networks. Configure a relay before production.

## AI and transcription

Browser speech recognition is used when available. Otherwise, complete audio segments can be uploaded to Whisper; configure `OPENAI_API_KEY` for this fallback. Optional provider settings are in `backend/.env.example`. Gemini uses `@google/genai`.

AI routes have per-user limits. Audio uploads are limited to 20 MB and supported media types. Text, context, provider timeouts, and generated output are bounded. AI prompts treat meeting content as untrusted evidence. Review generated decisions and action items before relying on them.

Transcript writes are serialized, coalesce interim updates, and retry transient failures with backoff. Persistence failures are shown to the user, who can export captions. Supabase stores transcripts, generated intelligence, and AI chat history. Regular meeting chat is transient and is removed when a room empties. Recordings are downloaded locally.

## Validation

From the repository root:

```sh
npm run check
npm audit --prefix backend
npm audit --prefix frontend
```

The check command runs strict lint for both applications, regression tests, and a production build. Tests cover signed sessions, access control, transcript ownership, request limits, cross-room signaling, temporary TURN credentials, malformed AI responses, transcription cleanup, retry ordering, and SQL migration behavior. SQL tests use PGlite's PostgreSQL engine without contacting the live database.

GitHub Actions repeats checks on pushes and pull requests. Dependency audits identify known advisories at the time they run; a passing audit is not a security certification.

### Responsive browser checks

```sh
npm run test:e2e --prefix frontend
```

Playwright tests the landing page, dashboard, and meeting controls across widths of 320, 375, 768, 844 (landscape), 1024, 1440, 1920, and 2560 pixels in light and dark themes. The suite checks horizontal overflow, visible touch controls, keyboard dismissal, message delivery across two browser contexts, and WCAG A/AA rules using axe. Screenshots and traces are written to `frontend/test-results`; the interactive report is `frontend/playwright-report/index.html`.

On Windows the tests use an isolated headless Edge instance. On Linux, run `npx --prefix frontend playwright install --with-deps chromium` first. GitHub Actions installs Chromium and runs these tests on Node 24.

The browser suite compiles its own isolated UI build and uses a separate local backend. Clerk is replaced only inside that test configuration, and microphone/camera input is synthetic. Production builds use the actual Clerk SDK and enforce real session verification. Real identity-provider login, TURN connectivity on separate networks, physical-device permissions, and paid AI calls still need staging validation.

The updated workspace supports meeting-link parsing, labeled media preferences, per-account recent meetings on the current device, and validated calendar invitations downloadable as `.ics`. Scheduling creates an invitation; it does not send emails or automatic reminders. Fonts are bundled locally rather than fetched from Google Fonts.

## Operations and scale

`/api/status` reports liveness and capability flags; `/api/ready` checks database access. Errors include request IDs and hide internal server details. SIGTERM/SIGINT trigger graceful shutdown.

The current deployment supports **one backend instance**: signaling, room chat, and rate-limit counters use memory. WebRTC uses a peer-to-peer mesh, with a default limit of 12 participants (`MAX_PARTICIPANTS`). Before horizontal scaling, add shared Socket.IO presence/adapter and shared rate-limit storage. Larger meetings require an SFU. Configure hosting monitoring, backups, and a data retention policy before a public production launch.

Repository checks do not deploy the app, migrate the live database, validate provider accounts, or replace real-device call testing.
